Modern Cross-Platform Operating System Architecture
===================================================

Purpose
-------
This document summarizes a proposed operating system architecture for mobile,
desktop, embedded, wearable, and AI-assisted computing. The detailed design is
organized under docs/ as Markdown files.

The system is designed around these goals:

1. Run across many CPU families and hardware platforms, including heterogeneous
   processors with performance cores, efficiency cores, DSPs, NPUs, GPUs, and
   secure enclaves.
2. Provide strong isolation between applications, drivers, system services,
   virtual machines, containers, user profiles, and sensitive data domains.
3. Maintain a stable, extensible system call ABI that can survive decades of
   platform evolution without copying the accidental complexity of older UNIX
   and Linux interfaces.
4. Treat observability, debugging, tracing, logging, crash diagnosis, and field
   repair as first-class operating system facilities rather than optional tools.
5. Prepare for AI-native and wearable-era workloads: local inference,
   multimodal sensors, continuous context, strict power budgets, privacy
   boundaries, and seamless device-to-device continuity.

Architectural Summary
---------------------
The OS uses a hybrid architecture:

- A small privileged kernel owns scheduling, virtual memory, low-level IPC,
  interrupt routing, capability enforcement, kernel object lifetimes, and the
  minimal hardware abstraction needed to boot and isolate the machine.
- Most policy lives outside the kernel in versioned, restartable services:
  storage, networking, graphics composition, media, update, identity, app
  lifecycle, package management, telemetry, AI runtime policy, and device
  management.
- Device drivers run in isolated user-space driver hosts by default. Drivers
  that require very low latency can use narrow in-kernel fast paths, but only
  behind stable driver contracts, verifier rules, IOMMU isolation, and typed
  capability checks.
- Hardware-specific code is confined to architecture ports, platform support
  packages, and hardware description bindings. Core services interact with
  hardware through typed device objects, resource graphs, power domains,
  security domains, and versioned driver protocols.
- Applications and services interact with the kernel through a capability-based
  handle model rather than global ambient authority. A process can only operate
  on objects for which it holds explicit handles and rights.

Major Subsystems
----------------
Kernel:
  The kernel provides virtual address spaces, threads, scheduling classes,
  timers, futex-style waits, interrupts, IPC channels, shared memory objects,
  handle tables, capability checks, IOMMU coordination, and secure boot
  measurement handoff.

Hardware abstraction:
  CPU architecture ports implement only the mandatory primitives: trap entry,
  context switching, page tables, atomics, timers, interrupt controllers, boot
  handoff, cache maintenance, and architecture-specific security controls.
  Platform support is described by ACPI, Device Tree, PCIe discovery, USB
  discovery, firmware tables, and OS-specific typed hardware manifests.

Drivers:
  The driver framework provides lifecycle management, version negotiation,
  resource binding, DMA mediation, power management, hotplug, crash recovery,
  tracing, firmware loading, and user-space driver hosting. Driver classes cover
  storage, filesystems, networking, USB, PCIe, graphics, display, multimedia,
  audio, camera, sensors, haptics, biometrics, secure elements, and AI
  accelerators.

System call ABI:
  The system call interface is small, object-oriented, and versioned. It uses
  handles, rights masks, structured arguments with size fields, explicit flags,
  monotonic extension rules, stable error domains, and forward-compatible
  negotiation. It avoids unbounded ioctl-style escape hatches as the primary
  extension mechanism.

Security:
  Security is based on capabilities, mandatory sandboxing, measured boot,
  signed system components, per-service least privilege, hardware-backed key
  storage, memory-safe system services where practical, verified driver entry
  points, and auditable policy. The model assumes hostile applications,
  vulnerable drivers, compromised peripherals, malicious files, and untrusted
  networks.

Virtualization:
  The OS treats virtualization as a core feature. It supports type-1 and type-2
  hypervisor deployments, confidential VMs where hardware supports them,
  containers built on namespaces and capabilities, virtual devices, paravirtual
  I/O, VM-aware scheduling, and explicit separation between host, guest,
  management, and device-emulation components.

Observability:
  Every major subsystem is designed with structured logs, event tracing,
  counters, crash dumps, health checks, timeline correlation, kernel and
  user-space probes, symbol management, privacy filtering, and remote diagnosis
  hooks. Production observability is controlled by policy so it can diagnose
  failures without leaking sensitive user data.

Lessons From Existing Operating Systems
---------------------------------------
Linux demonstrates the value of portability, hardware enablement, open
development, a large driver ecosystem, and pragmatic performance engineering.
It also shows recurring maintenance challenges:

- A very large monolithic kernel increases the blast radius of driver bugs.
- The syscall ABI is stable but contains decades of uneven interfaces.
- ioctl proliferation moves subsystem-specific ABI design into ad hoc command
  spaces that are difficult to validate and evolve.
- In-kernel drivers give excellent performance but make isolation, recovery,
  and security auditing harder.
- Multiple hardware description mechanisms and board-specific quirks create
  long-term maintenance cost.
- Distribution fragmentation complicates application deployment, debugging,
  updates, and support.
- Security features are powerful but often layered on after the fact, which
  creates inconsistent policy surfaces.
- Observability is strong for experts but can be hard to use consistently
  across kernel, drivers, services, desktop stacks, mobile stacks, containers,
  and virtual machines.

This architecture uses those lessons directly:

- Keep the kernel smaller and more enforcement-oriented.
- Move most drivers and policies into isolated, restartable services.
- Design stable typed ABIs up front.
- Treat hardware description as a schema-governed contract.
- Make sandboxing, capabilities, update integrity, and tracing baseline system
  properties.
- Provide one system architecture that scales down to wearables and up to
  workstation, server, and virtualized deployments.
