# Build Graph

Bazel (via Bazelisk, pinned in `.bazelversion`) is the authoritative build:
kernel, checks, lints, and the bootable image are one graph
(`docs/lifecycle/02-build-and-test-infrastructure.md`). The cargo workspace
is the developer inner loop only; nothing cargo produces is shipped.

- `platforms/` — the bare-metal target platforms (`x86_64-kernel`;
  and `aarch64-kernel`, one bare (os:none) platform per CPU family; the
  architecture is a `tessera_kernel_binary` attribute, not a `select()`).
- `rules/platform_transition.bzl` — transitions kernel binaries to their
  platform so a plain host `bazel build //...` builds everything.
- `rules/kernel.bzl` — `tessera_kernel_binary`: rust_binary with the
  kernel codegen flags and linker script.

Common commands:

```bash
bazel test //...                  # tiers 0 + 1 + 3
bazel build //... --config=lint   # full-graph rustfmt + clippy aspects
bazel test //tools/qemu:smoke_boot_test --config=kvm   # KVM-accelerated
bazel build //kernel/image:tessera_iso                 # bootable ISO
```

| D91 | **The driver framework begins: drivers bind to devices they did not hardcode (M52).** Before this, a driver knew its device by a compiled-in handle number boot happened to install — `BLK_DEVICE_HANDLE = 0`. That is not binding, it is a constant shared between two files, and it fails the moment the machine has its devices in another order, two of a kind, or one fewer. Now a new ring-3 **device manager** (`userspace/device-manager`, the third EL0 program) holds a capability to *every* device boot discovered, and nothing else grants any driver anything; a driver names a **class** over an ISL channel protocol (`api/isl/examples/driver_bind.isl`) and is handed a capability to a device of that class, or told there is none. **Enumeration is why the manager is a program and not a table:** every virtio-mmio node on this machine carries the same device-tree `compatible` string, so the class exists only in a register — the manager maps each capability it holds, reads the magic and `device_id`, and records what it found. That is equally true of PCIe config space, so this is not a virtio quirk. **What deliberately does not cross the wire:** no MMIO base, no length, no interrupt. All three live inside the capability and the kernel reads them from there on `MapDevice`; a driver that could name its own window would not need a capability. The reply's real payload is the transferred handle. **Exclusivity needs no flag:** a transfer is a `take` from the sender's table, so a device can be handed out exactly once — one-driver-per-device is a property of capability conservation, and the manager could not violate it if it tried. **Two things the build taught, both of which the rights model was right about.** First, the initial boot failed `AccessDenied` because `HandleTable::take` requires `Rights::TRANSFER`: *handing a capability to another process is itself a right*, and boot now grants it to the manager and nowhere else. Second, the integrated boot then **deadlocked**, and the diagnosis is worth keeping because the symptom was nothing at all — no fault, no error return, no output, both parties parked. `Executive::reply` hands off to the caller and leaves the replier **Blocked**, which is correct only for a server whose next wake is the next call on that same endpoint, because `call` wakes a peer only if it registered itself via `receive`. A server that replies and loops back to `recv` is Blocked *without being a registered receiver*, so the second request finds no waiting receiver, blocks too, and neither side runs again — the first request succeeds silently, which is what makes it look like a hang rather than a bug. The manager uses **`ChannelReplyContinue` (D85)**, which was built for exactly this shape. This is the second time this trap has been hit (the first is recorded at D85); it is now recorded as a property of `reply` rather than of any one caller. **Verification:** 38/38 tests, lint and fmt clean, 5/5 AArch64 boots deterministic with every prior verdict intact, and the other four ports byte-identical. Negative check: making the manager misclassify block devices → the driver's Block bind returns "no such class" → it refuses to proceed → exit 65 with `0xdead…0040_0101`, proving the driver does not fall back to driving whatever handle 5 happens to be. **v0 deviations:** the manager **keeps the MMIO mapping** of devices it has handed away, because there is no syscall to unmap a device window — enumeration requires access, and the grant it makes is real while the mapping it already made is not revoked; **rights do not narrow on transfer**, so a driver inherits `TRANSFER` and could re-delegate; the *bootstrap* handle numbers are still install-order constants in both programs (what changed is that none of them says which device anything is); binding is by class only — no manifests, no `compatible`-string matching, no PCI IDs; **no restart** (a driver that dies does not re-bind); one class per request and no unbind; and the framework exists on **AArch64 only**, the one port with ring 3. | Device-window revocation, so a transferred capability takes its mapping with it; rights narrowing on transfer; driver manifests as data (class + match keys + required resources) so binding is a match rather than a class lookup; restart and re-bind under the failure model; handle discovery, so even the bootstrap numbers stop being constants; PCIe/ECAM enumeration beside virtio; ring 3 on the other ports so the framework is not AArch64-only. |
