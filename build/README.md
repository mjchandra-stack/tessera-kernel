# Build Graph

Bazel (via Bazelisk, pinned in `.bazelversion`) is the authoritative build:
kernel, checks, lints, and the bootable image are one graph
(`docs/lifecycle/02-build-and-test-infrastructure.md`). The cargo workspace
is the developer inner loop only; nothing cargo produces is shipped.

- `platforms/` — the bare-metal target platforms (`x86_64-kernel`;
  and `aarch64-kernel`, one bare (os:none) platform per CPU family; the
  architecture is a `tessera_kernel_binary` attribute, not a `select()`).
- `rules/platform_transition.bzl` — transitions kernel binaries to their
  platform so a plain host `bazel build //...` builds everything.
- `rules/kernel.bzl` — `tessera_kernel_binary`: rust_binary with the
  kernel codegen flags and linker script.

Common commands:

```bash
bazel test //...                  # tiers 0 + 1 + 3
bazel build //... --config=lint   # full-graph rustfmt + clippy aspects
bazel test //tools/qemu:smoke_boot_test --config=kvm   # KVM-accelerated
bazel build //kernel/image:tessera_iso                 # bootable ISO
```

| D107 | **Ring 3 on RISC-V 32 — the fourth architecture with a privilege boundary (M68).** The port enters U-mode, serves a syscall, and contains a user fault instead of dying of it. `UserContextOps::init_user`, the user trampoline, the trap vector's `sscratch` swap and `sstatus.SUM` all arrive together, and D106's empty user half is what makes the last of the three checks mean anything. **Almost all of it transferred from D98, and where it did not is instructive.** The mechanism is identical at half the register width: `sw`/`lw` instead of `sd`/`ld`, a frame of 84 bytes reserved as 96 (the ABI wants 16-byte alignment at both word sizes), and `sstatus.SPP` at bit 8 and `SUM` at bit 18 — `sstatus` is narrower here but neither bit is one that moved. `satp` is the real difference: Sv32 puts `MODE` in a single bit 31 rather than a four-bit field, and its `PPN` is 22 bits against Sv39's 44, so `prepare_resume` shifts a 34-bit physical root into a 22-bit field — safe only because `build_kernel_space` already refused any space whose root sat above the 32-bit window (D89). **The `sscratch` invariant holds here for the same structural reason** — the value is *derived* at every exit to U-mode from the stack pointer the exiting code is standing on, so it is not state the context switch must carry (D98's finding, now confirmed at a second word size rather than assumed to generalise). `SUM` likewise cannot be scoped per copy, for D101's reason: a copying syscall may block and hand off inside the window. **Proven at boot** (`umode:` verdicts, D58-gated, in dependency order): entering U-mode and returning — two syscalls, a value round-tripped through the kernel *and* the user stack with a clobber in between, so neither a stale register nor an unmapped stack can pass; **W^X at the unprivileged level** — a store into the read-execute code page takes a store page fault, the address checked against the page; and **the privilege boundary** — a user load of `USER_ADDRESS_MAX` itself takes a load page fault, which is the exact address D106 emptied down to. The program is position-independent, reading its own address with `auipc`. **Three negative checks, all behaving exactly as they did on the 64-bit port:** `.user()` dropped from the code mapping → the program cannot be fetched → check 6; dropped from the **stack** mapping → same, which only bites because the program was written to use its stack; and the handler's `sepc += 4` removed → the `ecall` re-executes forever and the boot **hangs rather than failing**, recorded as what it is. That the failures match D98's one for one is itself worth something: it is evidence the two ports share a mechanism rather than two implementations that happen to agree. **Verified:** 39/39 tests, lint/fmt clean, 9/9 conformance, exit 33, five boots byte-identical; x86-64, AArch64, ARM 32-bit and RISC-V 64 artifacts byte-identical. **Four of five architectures now have a privilege boundary**; ARM 32-bit is the last without one. **v0 deviations:** U-mode runs in the **kernel's own address space**, with the user pages in the (now empty) user half and every kernel page lacking `U` — a real boundary in one table, but no per-process root yet, so `prepare_resume`'s `satp` write is implemented and unexercised; a hand-written blob rather than an ELF; a two-call ABI in the boot glue rather than kcore's syscall substrate; cooperative, with a fault or exit abandoning the thread mid-trap; and no FP state. | Per-process Sv32 roots over the empty user half; then the kcore substrate and channel IPC, following D99-D101; and ring 3 on ARM 32-bit, the last port without it. |
| D108 | **Per-process Sv32 roots on RISC-V 32 (M69).** Two processes, each with its own translation root, running the same program: the same virtual address reads different memory in each, and neither can reach the kernel that is mapped in both. D106 emptied the user half for exactly this, and it makes `prepare_resume`'s `satp` write — implemented and unexercised in D107 — the thing that actually switches a process. **`new_user` copies the kernel's root entries by value**, the Sv32 twin of D99: one `satp`, so "the kernel is mapped in every address space" is not a policy a kernel could choose against. Sv32's shape changes the arithmetic without changing the argument — two levels rather than three, a 1024-entry root whose every entry covers 4 MiB, and the boundary at slot 512. **ASIDs are 9 bits here against Sv39's 16**, a smaller pool for the same job, so `new_user` refuses one that does not fit rather than truncating it into a collision. **Everything about this milestone matched the 64-bit port's, including both of its lessons arriving unchanged.** Teardown is counted **exactly** (root + one leaf table per distinct 4 MiB region: A maps four, B three, so 5 + 4 = 9, right on the first boot) because a lower bound cannot see a teardown that also freed the shared kernel tables — and the negative check that breaks `free_tables` fails on check 17, exactly as D99's did. The code frame is deliberately **shared** between the two processes, so the isolation on show is a property of the tables and not of the memory happening to differ. And the private-page check is made in **both** directions, because "B faults" alone would also hold for an address neither maps. **Three negative checks, and the third is the same honest non-result as D99's:** `new_user` not copying the kernel half → the kernel vanishes at `activate` and the boot **hangs**, because there is nothing left to report with; `free_tables` walking the whole root → check 17; and removing the leading `sfence.vma` for an ASID-owning space → **still boots clean**, because QEMU's TCG flushes the whole TLB on every `satp` write. ASID-scoped flushing is therefore implemented and **unverified in-repo on this port too** — the fence is there because the architecture requires it, not because anything here would notice its absence. **Verified:** 39/39 tests, lint/fmt clean, 9/9 conformance, every D106-D107 verdict intact, exit 33, five boots byte-identical; x86-64, AArch64, ARM 32-bit and RISC-V 64 artifacts byte-identical. **v0 deviations:** the spaces are built and switched by the **boot glue**, not by kcore — no `Process`/`Thread`/`Scheduler` on this port yet, so a "process" here is a root plus a hand-run user thread; ASID allocation is two constants with no recycling or wrap handling; `prepare_resume` still cannot carry an ASID, since the trait hands it only a `PhysAddr`, so a resume through it flushes more than it needs to; and the kernel space keeps its user-half mappings from D107. | kcore `Process`/`Thread`/`Scheduler` on this port, then the Executive and channel IPC — D100 and D101's sequence; an ASID allocator with recycling; hardware validation of the ASID-scoped fence, which no emulator here distinguishes. |
| D109 | **Ring 3 on ARM 32-bit — the architecture matrix now has a privilege boundary everywhere (M70).** The fifth and last port enters User mode, serves an `svc`, and contains a user abort instead of dying of it. All five families can now run unprivileged code. **This is the port where the porting layer earned its keep, because almost nothing transferred.** ARMv7-A **banks `SP` and `LR` per processor mode**, which does two thirds of the job for free and one third not at all. For free: entering SVC mode gives the kernel its own stack and leaves the user's untouched, so there is no swap-through-a-scratch-register dance — `SP_svc` *is* the current thread's kernel stack, because the context switch left it there. Not at all: the user's banked pair is unreachable by ordinary means, so the `svc` vector saves and restores it with the **`^` form** of `stm`/`ldm`, which forbids writeback (hence a separate address register) and must not be followed by an instruction touching a banked register (hence the `nop` — an architectural hazard, not decoration). **Two more differences the other four ports do not have.** `LR` on an `svc` already points *after* the instruction, so the syscall handler advances nothing — the exact opposite of RISC-V, where forgetting to advance `sepc` livelocks; the negative check here is to *rewind* `pc` onto the `svc`, which produces the same hang from the mirror-image mistake. And an abort arrives in **abort mode on the abort stack**, not on the faulting thread's kernel stack, so the vector switches to SVC mode (`cps #0x13`) before calling the handler: containing a fault means switching context, and doing that from abort mode would leave the CPU in it, so the next abort would overwrite the frame this one was standing on. **The boundary is `AP`, not the address, and that changes what the third check must probe.** RAM begins at 1 GiB here — *below* `USER_ADDRESS_MAX` — so unlike RISC-V 32 (D106) the kernel and the user program share the low half, exactly as AArch64's first EL0 milestone did (D70). Kernel pages are `AP_RW_PL1` and user pages `AP_RW_ALL`. So the privilege check reads a **mapped** kernel address and requires a *permission* fault; the check refuses to run at all if that address is not mapped, because an absent one would fault for the wrong reason and prove nothing. The paging layer needed no change: `leaf_attributes` has encoded user pages correctly since D90, including the `PXN` that keeps privileged code out of them — bit 54 being plain `XN` here rather than AArch64's `UXN` is why that was already right. **Proven at boot** (`umode:` verdicts, D58-gated): entering User mode and returning — two `svc`s, a value round-tripped through the kernel *and* the user stack with a clobber in between, so neither a stale register nor an unmapped stack can pass; **W^X at the unprivileged level** — a store into the read-execute code page takes a data abort inside that page; and **the privilege boundary** — a user load of mapped kernel memory takes a data abort. The program is position-independent, computing its own address with `adr`. **Three negative checks, all biting:** `.user()` dropped from the code mapping → the program cannot be fetched; dropped from the **stack** mapping → the stack round trip faults, which only bites because the program was written to use its stack; and the syscall hook rewinding `pc` → livelock. **Verified:** 39/39 tests, lint/fmt clean, 9/9 conformance, exit 33, five boots byte-identical; x86-64, AArch64, RISC-V 64 and RISC-V 32 artifacts byte-identical. **v0 deviations:** User mode runs in the kernel's own `TTBR0` with the program mapped alongside it — a real boundary in one table, but **no per-process isolation** and no `TTBR0`/`TTBR1` split, so `prepare_resume` is still the trait's no-op here; a hand-written blob rather than an ELF; a two-call ABI in the boot glue rather than kcore's syscall substrate; cooperative, with a fault or exit abandoning the thread mid-trap; and no FP/SIMD state. | The `TTBCR` split and per-process `TTBR0` roots, which this port needs before kcore processes; then the kcore substrate and IPC, as D100-D101; an ELF loader. |
| D110 | **ARM 32-bit gets the `TTBCR` split and per-process `TTBR0` roots (M71).** The kernel moves into the high half and is walked out of `TTBR1`; each process gets its own `TTBR0`. Two processes run the same program at the same addresses and read different memory. This was planned as two milestones and **landed as one, because on this port they are not separable**: the moment the kernel's space becomes `TTBR1`-only it can no longer hold a low address at all, so D109's user checks stop working until there is a process space to put them in. Discovering that is the milestone's first finding. **The split had to be a relocation.** `TTBCR.T0SZ = 0` gave `TTBR0` the whole 32-bit space, and LPAE can only put `TTBR1` at the *top* in a power-of-two region — while the kernel was linked at 0x4001_0000, because RAM begins at 1 GiB. There is no split that leaves it there. So the image now links at `KERNEL_VIRT_BASE + phys` with `KERNEL_VIRT_BASE = 0x8000_0000`, `T0SZ = T1SZ = 1` splits the space 2 GiB / 2 GiB, and the entry stub fills **two** boot roots (identity in `TTBR0` so it can keep running, high in `TTBR1` where the kernel is linked), enables the MMU and jumps high. It stays position-independent by loading each symbol PC-relative and subtracting the known `KERNEL_VIRT_BASE` — no relocation machinery for a constant offset. `USER_ADDRESS_MAX` stops being the policy number D90 apologised for and becomes a hardware boundary. **The bug that mattered, and it was not in the stub.** With a 2 GiB region a level-1 index is **one bit**, so `0x0900_0000` and `0x8900_0000` reach the same root entry — and a `TTBR1` space asked to translate a device's *physical* address cheerfully described the direct-map alias instead. The split's own assertion caught it. A space now carries the base of the region its root is walked for and refuses an address outside it, which makes `translate` exact and `map` refuse to put a low address in the high half. The negative check removes that guard and the assertion fails; another maps the user image into the kernel's space and is refused at map time. **Per-process roots are much smaller here than on the RISC-V ports, structurally.** Two translation-base registers mean a process root holds **only** the user half: no kernel entries copied by value, nothing shared by pointer, and no exact-frame-count teardown guard needed against over-freeing (D99, D108). `free_tables` can free everything the root reaches, because everything it reaches belongs to the process. **Supporting changes.** `leaf_attributes` now emits **`nG`** — it had ignored `PageFlags::global()` entirely, so every descriptor was global, which is harmless with one address space and would have silently defeated ASIDs with several; added and verified alone first, with boot output unchanged. `karch-arm-common` gains the device access window D97 gave its RISC-V counterpart, because the GIC names itself physically and ARM 32-bit no longer has an identity map to reach it through; AArch64 leaves the window at zero. **Negative checks: two bite, one does not, and the one that does not is this port's own doing.** Removing the region guard → the split assertion fails; mapping a user address into the kernel space → refused. But giving both processes the **same ASID** changes nothing, because `activate` invalidates the *entire* TLB on every `TTBR0` change — so ASIDs currently buy nothing here and are recorded as unverified.
